# M6d：日志增长与恢复基线

这是检查点开发前的测量切片，接在 [M3d 主会话上下文压缩](superagent-m3d.md)
之后。只新增离线 fixture、测试、基准和合同说明，不改变运行时、Journal 接口、
日志格式、数据库依赖或任何已有记录。

## 先区分两个问题

- **模型上下文。** M3d 缩短未来模型请求中保存的历史，避免超预算后持续失败。
- **存储与恢复。** 每次主会话决定仍将当时的完整快照写进追加日志。旧快照没有
  被删除，JSONL/SQLite 打开时会读取记录，协调器再按序重放。固定大小的快照
  导致总量随次数增长；每轮增长的快照会反复保存先前内容，放大累计日志大小。

基准使用公共协调器 API 和确定性自定义 Router 生成已结束的输入，不进行 Pi
推理，也不调用模型供应商。两组快照分别保留一条 4 KiB 文本消息，或每轮增加
一条 256 字节文本消息；JSON 结构和时间戳另占空间。它们是可控的快照负载，不是
真实会话、用户内容或模型 token。100 与 1,000 条输入用于比较增长趋势，不代表任何
线上容量承诺。后台执行、真实信道和多主机数据库不是这个负载的组成部分。

## 测量边界

fixture 的生成、写入和准备不计入计时；分开测量 JSONL 打开/解码（不含 Close）、
`Log()` 返回独立副本，以及已打开 Journal 上的协调器重放。记录每次操作的耗时、累计分配
字节和分配次数，同时报告日志总字节、记录条数与每输入字节数。

`B/op` 是本次操作的累计分配量，不是进程常驻内存或峰值内存。已打开日志仍在
内存中，文件系统缓存也可能命中；这些结果不是冷盘启动、真实模型性能、吞吐或
跨平台比较。重放包含其必须的 Log 副本，不能把各项耗时相加宣称完整启动时间。

### 2026-11-06 远程 Linux 基线

Go 1.26.10，Linux/amd64，共享远程运行环境。每个叶子基准执行一次操作并重复
三次，下表为三次中位数；早期样本与包级验证有时间重叠，CPU/GC/文件缓存并未
隔离。这是识别数量级和成本位置的诊断，不是受控性能验收或优化前后对照。

```sh
go test -mod=readonly ./superagent -run '^$' -bench '^BenchmarkJournalGrowth$' -benchtime=1x -count=3 -benchmem
```

| 负载 | 输入数 | JSONL 字节 | 打开 ms | Log 副本 ms | 重放 ms | 重放累计分配 B/op |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| fixed4KiB | 100 | 509,292 | 28.34 | 9.81 | 17.92 | 7,345,696 |
| fixed4KiB | 1,000 | 5,099,606 | 459.99 | 95.50 | 207.64 | 77,502,720 |
| growing256B | 100 | 1,872,166 | 130.55 | 35.44 | 67.95 | 30,460,552 |
| growing256B | 1,000 | 177,530,750 | 7,749.72 | 3,157.06 | 5,629.71 | 2,887,202,296 |

100/1,000 输入分别产生 202/2,002 条日志记录。完整矩阵通过，用时约 134 秒，
含 fixture 准备和各阶段多次打开。全部样本与分配次数见
[原始记录](benchmarks/superagent-journal-growth-20261106.txt)。

固定消息大小的日志随输入量近似线性增长；累加消息的夹具在十倍输入下，日志
由约 1.87 MB 增至 177.53 MB。后者的 Log 副本本身就花费约 3.16 秒，重放累计
分配约 2.89 GB，但不能据此声称需要 2.89 GB 常驻内存。下一项可先评估已验证
记录的独立副本能否避免再次整段 JSON 序列化，保留 copy-on-read 合同；这是比
新检查点格式更窄的优化，不会减少磁盘日志体积。检查点设计仍需下述身份合同。

## 检查点不能伪装成截断后的旧 Journal

当前 [`Journal`](../superagent/journal.go) 规定记录从 1 开始连续编号、ParentID
连接前一条记录，返回完整已提交日志。[restore](../superagent/superagent.go)
从空状态按序应用每个 transition。DeliveryID 与部分 HistoryRef 由准入位置生成，
报告读取会把该位置还原到原事件；任务 ID 和后续日志 ID 也依赖已恢复的计数。

因此，简单删掉旧记录、重新编号或只保存最后快照不能满足现有合同。完整导出
`Header()` + `Log()` 可以保存历史身份，属于备份/迁移，不是压缩，也不会减少
恢复必须处理的状态。不能复制旧租约为目标存储的有效执行权限；目标必须自行
取得新的所有权。

未来若数据证明需要检查点，先定义新的启动合同及版本，再选择实现。至少保留：

- 授权域、主会话和 Provider 会话身份；日志头、准入位置、任务和决定计数。
- 入站去重键及原内容、冻结 fanout 顺序、待路由输入、已消费位置、任务队列。
- 最新主/Worker 快照、任务状态、审核屏障、精确控制与更正的原执行证据。
- 报告顺序与 DeliveryID、回复/尝试/未知发送、已确认平台消息和限流事实。
- Thread 订阅、交回记录、公开历史引用及其可见范围；私有输出仍不公开。
- 后台操作原 ID/调用/授权/配额/回执、未知或运行中状态、唯一完成事件。
- Watchdog 配置、巡检位置、finding/干预事实、后续观察流与原序号；渠道和设备各自的独立日志不因
  协调器检查点自动迁移或取得新的执行权限。

检查点本体、基线日志头与后续尾日志必须原子绑定，失败或失租不能发布半个
状态。新格式应能拒绝不支持的版本。上线前使用现有中断/未知结果/失租夹具对照
完整重放和检查点恢复，而不是只比较“最终文本相同”。

历史归档策略要单独决定：保留全部公开历史就仍需可访问的原文或兼容索引；只
保存最新热状态不能同时声称无界历史召回。当前 continuation cursor 的认证密钥
在重启后重新生成，不能把它误写为需跨重启沿用的稳定历史身份。

## 本切片的结论限制

本次不引入检查点、删除/归档策略、流式 Journal、数据库适配或新的恢复模式。
先用可重复数据确定主要成本，再提出能保留上述身份的窄实现。临时测试文件不
接触业务数据库；没有真实模型、生产服务、用户电脑、CI、部署或额外付费调用。

新增回归核对原 Header/逐条日志、主/Worker 会话与快照、报告/待交付回复、真实
HistoryRef、去重与变更内容冲突、私有内容不可见，以及纯恢复不回调或追加日志。
定向回归、整个 SuperAgent 包 race 和 vet、gofmt/空白检查通过；独立审查无阻塞
项。此切片仅新增测试和文档，沿用前一切片的全仓检查，没有重新声称完整根库
race、SQLite 测量、Windows/macOS 或真实宿主验收。

后续 [M6f 检查点评估](superagent-m6f.md) 明确了侧文件缓存的状态绑定、旧读者和无界历史限制；没有引入删记录或新恢复格式。当前先收窄为保留全部校验与归一化语义的恢复路径优化，不能把它称为有界存储已完成。
